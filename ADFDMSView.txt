1. WHAT IT DOES
----------------------------------------------------------------------------------------------------

ADFDMSView opens Amiga disk images in Far Manager as if they were folders. An ADF disk
image (OFS or FFS file system) or a DMS disk archive appears as a virtual panel in which you
can:

  - browse the directory tree of the Amiga disk;
  - view files (F3);
  - copy files, and whole directories with everything under them, to an ordinary folder (F5), with
    their original Amiga date and time.

What sets the plug-in apart is that it keeps working on damaged material. Old floppy disks and old
archives are often truncated, bit-rotted, or have lost a few bytes. The plug-in checks what it
reads, repairs what can be repaired, brings back files that the directory tree no longer reaches,
and tells you, item by item, what is complete, what is partial and what is lost.

The plug-in is read-only: nothing is ever written to the image or to the archive.


2. REQUIREMENTS AND INSTALLATION
----------------------------------------------------------------------------------------------------

  - Far Manager 3.0 (build 3000 or later), 32 or 64-bit: use the DLL of the same bitness as Far
    (x86\ADFDMSView.dll or x64\ADFDMSView.dll).

  - Put ADFDMSView.dll and the language file (ADFDMSViewEng.lng) together in a
    folder of their own under the Far plug-ins folder, for example

        %FARHOME%\Plugins\ADFDMSView\

    and restart Far. Far looks for the language files in the folder of the DLL, so the folder
    must not be shared with another plug-in.

  - To open a disk, put the cursor on a .adf or .dms file and press Ctrl+PgDn (Enter may do
    the same, depending on the file associations you have defined).

  - Far offers a file to the plug-in by its extension: any .adf file is opened; a .dms file
    is opened if its content looks like a DMS archive (the check also accepts an archive whose
    signature or first track header is damaged).
  - If the plug-in recognizes a file but cannot open it (an archive that does not hold a disk
    image, ...), a box says why (section 3) and Far does nothing else with the file.


3. SUPPORTED FORMATS
----------------------------------------------------------------------------------------------------

ADF disk images (.adf)

  - Raw dumps of Amiga disks with the OFS or FFS file system. The usual sizes are 901,120 bytes
    (DD, 880 KB) and 1,802,240 bytes (HD, 1760 KB), but any image of at least 8 blocks (4,096
    bytes) is accepted, up to 512 MiB.
  - Bootblocks DOS\0 to DOS\7. Every flavor that means FFS (DOS\1, \3, \5, \7) is read as FFS. The
    international and directory-cache variants are read through the normal hash tables.
  - Files of any size, including files of more than 72 blocks (the extension blocks are followed),
    and any number of entries per directory.

DMS disk archives (.dms)

  - DMS archives of a floppy disk, with every compression mode: no compression, simple (RLE),
    quick, medium, deep, heavy 1 and heavy 2.
  - Standard 80-cylinder DD and HD disks, and the layout of 160 half-cylinder tracks of 5,632
    bytes.
  - The archive is unpacked in memory into a disk image, which is then read like any ADF.
  - An archive whose signature or first track header is damaged is still recognized and read.
  - Encrypted archives (a password was set when they were made) are opened: the plug-in does not
    ask for the password, it finds the key itself (section 5).

Not opened (a box says why, and Far does nothing else with the file):

  - DMS archives that do not hold a disk image (disk type 7);
  - DMS archives in which no disk track can be found, and encrypted DMS archives whose key is not
    found and from which nothing can be decoded;
  - files that cannot be read, shorter than 56 bytes or larger than 512 MiB;
  - a file for which there is not enough memory.

While Far searches inside archives, or works silently, no box is shown and the file is simply
declined, so that other plug-ins can try it.


4. USING THE PANEL
----------------------------------------------------------------------------------------------------

Browsing and copying

  - Enter goes into a directory; ".." goes back up, as far as the root of the disk.
  - F3 views a file (Far extracts it to a temporary folder first).
  - F5 copies the selected items. A selected directory is copied with all its subdirectories.
    A dialog like the copy dialog of Far asks where to copy: the folder of the other panel is
    proposed; a relative path is taken from it, a folder that does not exist is made, and the
    previously entered destination paths can be recalled with Ctrl+Down.
  - "Already existing files" says what to do with a file that is already at the destination: Ask
    (a box for every such file, with Overwrite, Skip, Overwrite all, Skip all and Cancel),
    Overwrite, or Skip. The choice is proposed again until Far is closed. Cancel in the dialog, or
    in the box, copies nothing more. If the dialog itself cannot be shown (not enough memory), a
    box says so and nothing is copied.
  - F3 (view) and F4 (edit) copy the file to a temporary folder without a dialog.
  - A file that cannot be read completely is still copied: the blocks that cannot be read are
    replaced by zeros (the Description column says "incomplete or unverified blocks"). The same is
    said of a file in which a block was used although a check failed (a data block with a wrong
    checksum, a damaged header of the file). A block that belongs to another file, or to another
    place of the same file, is never copied into a file. A file of which nothing can be read is not
    copied, and neither is an item whose destination path would be longer than 259 characters; a
    file whose copy was cut short (the disk of the destination is full, for example) is deleted
    again. At the end a box tells how many items were copied incomplete or unverified and how many
    could not be copied.
  - The copies keep the date and time of the Amiga files and directories (the last modification
    date of the header block of the item): the date is set as the creation and last write time
    of the copy. A directory gets its date after its contents have been copied. The Amiga has no
    time zone: the clock value is taken as local time, so Windows shows the same date and time
    that the Amiga showed. The panel shows the same date in its Date/Time columns, so it can also
    be sorted by date. An item whose header has an impossible date (a damaged header) gets no
    date: the copy has the date of the moment of the copy, and so do the items that have no Amiga
    date (the unpacked <name>.adf, _RECOVERY_REPORT.txt, the folder _RECOVERED, DATA_<n>.bin).
    Files of _RECOVERED keep the date of their header block.

Read-only

  - Nothing can be changed in an image or in an archive. F5 or F6 into the panel, F7, F8, Del, the
    save of a file edited with F4, and F6 or Shift+F6 out of the panel (a move would delete the
    items from the image) show a box that says that the panel is read-only; nothing is done.
  - If a file edited with F4 cannot be saved back, Far keeps the edited copy in a temporary folder
    and says where it is.
  - To take items out of the panel, copy them with F5.

Names

  - Amiga names (Latin-1) are shown as Unicode names made valid for Windows. The characters that
    Windows does not allow (< > : " / \ | ? *) and the control characters (codes 0-31 and 127-159)
    become "_"; trailing dots and spaces become "_" (so "abc." is shown as "abc_", and a name made
    only of dots or spaces, such as ".", as "_"); the names that Windows reserves (CON, PRN, AUX,
    NUL, COM1-9, LPT1-9, also with the superscript digits 1, 2, 3 of Latin-1, and also followed by
    an extension, even after spaces, such as "CON .txt") get a "_" in front.
  - Two items of a directory that would get the same name (the case does not count, also for the
    accented letters) are told apart with "~2", "~3", and so on after the name that the second one
    had: "foo", "foo", "foo" are shown as "foo", "foo~2", "foo~3".
  - Items are shown as ordinary files and directories, with their date and time. Protection bits
    and file comments are not shown. Hard links and soft links are not listed.

Special items in the root of the panel

  <name>.adf                 Only for DMS archives: the disk image unpacked from the archive.
                             Copy it (F5) to get an ordinary ADF file for an emulator.
  _RECOVERED                 Only if something was recovered: the files and data blocks that the
                             directory tree does not reach (see section 6).
  _RECOVERY_REPORT.txt       Only if damage was found: a text that lists what the readers found and
                             repaired, one line per finding. Lines that start with "ERROR:" are
                             problems, lines that start with "note:" are repairs and other remarks.

Description column

  The Description column (the Descriptions panel mode, Ctrl+6 by default) tells what is special
  about an item:

    unreadable                                  nothing of the file can be read
    incomplete or unverified blocks             some blocks of the file cannot be read, or were
                                                used although a check failed
    size taken from the data blocks             the size field of the file was wrong
    recovered from the header                   a file of _RECOVERED
    data blocks without a header                a file of _RECOVERED made of orphan data blocks
    files and data not reached by the           the _RECOVERED folder itself
      directory tree
    unpacked disk image                         the <name>.adf item
    what was found and repaired                 the report

Panel title

  The title of the panel is "ADF: <file>" or "DMS: <file>". When the image or the archive had
  damage, "[damaged]" is added.

Information panel (Ctrl+L on the other panel)

  Container Format     ADF image, or DMS compressed (also "encrypted").
  File System          Amiga OFS or FFS (and whether the bootblock is not a standard DOS one).
  Disk Capacity        Size of the disk image in KB.
  Bad Sectors          Number of damaged blocks found while reading the file system.
  Bad Tracks           Number of damaged tracks (cylinders).
  Bad Track List       The numbers of those tracks (or "None (disk intact)").
  Root Block           valid / bad checksum (accepted) / missing (files recovered from headers, or
                       rebuilt from data blocks) / no readable DOS file system.
  Recovered            Files and groups of data blocks found outside the directory tree.
  Incomplete Files     Files that cannot be read completely or could not be verified, and files that
                       cannot be read at all.
  DMS Tracks           Tracks right, repaired, and not verified.
  DMS Tracks Missing   Tracks lost and tracks absent from the archive.
  DMS Headers          Track headers that were damaged and repaired.
  Details              Points to the report, when there is one.
  Dir Block / Items    Block number of the current directory and number of items in it.

  Some lines appear only when they apply: Recovered, Incomplete Files, DMS Headers, Details, and the
  DMS lines (only for archives). For an intact disk the list of bad tracks says
  "None (disk intact)".

An .adf file that is not an Amiga DOS disk

  It still opens, as a panel that holds only _RECOVERY_REPORT.txt, which says why the disk could
  not be read.


5. DAMAGED DMS ARCHIVES
----------------------------------------------------------------------------------------------------

Verification. Every track is checked twice: the CRC-16 of its packed data and the 16-bit checksum of
the unpacked track must be those written in the track header. The state of each track of the disk
is known:

    right          CRC and checksum are right (or the checksum alone, when the packed data are
                   damaged only in bytes that the decoder does not use).
    repaired       The header or the packed data were damaged and were repaired. After the
                   repair CRC and checksum are right.
    not verified   The packed data are intact (CRC) but the checksum of the track is not the
                   expected one. The track is kept. Also a track that depends on something that
                   is not completely verified: the first track of an encrypted archive when more
                   than one key fits it (the first bytes of the track are not certain) or when
                   the key fits only weakly (see Encrypted archives), and a track repaired by a
                   correction of bits that was found after a class of candidates was skipped (see
                   Packed data).
    best effort    The data are damaged and could not be repaired. What could be unpacked is kept:
                   the part before the damage is right, what could not be unpacked is zero.
                   Tracks that copy from such a track are kept the same way.
    lost           The track is in the archive but nothing could be recovered from it. It is
                   written as zeros.
    absent         The track is not in the archive. It is written as zeros.

A disk of 80 cylinders (DD or HD) is always written at its full size; missing tracks are zeros.
Tracks that are lost, best effort or not verified, and tracks that are absent although the archive
announces them, are counted as bad tracks.

Headers. A track header (20 bytes) damaged in one or two bytes, or only in its CRC field, is
repaired, so that the track, and the tracks that depend on it, are not lost. The archive is also
recognized when its "DMS!" signature or its first track header is damaged. When a header cannot be
repaired, the plug-in looks for the next valid track header and goes on from there.

Packed data. When the CRC of a track is wrong, the track is first unpacked as it is: if the
checksum of the unpacked track is right (the damage is in bytes that the decoder does not use),
the track is kept as right and nothing is searched. If it is not, the plug-in looks for what
damaged the data. The length of the data, between the track header and the next valid track
header, says which kind of damage to look for, and a repair is accepted only if the CRC of the
packed data and the checksum of the unpacked track are then both right. It repairs:

  - one byte that was lost inside the track data (the data are one byte shorter than the header
    says);
  - one byte that was added inside the track data (one byte longer);
  - one byte whose value is wrong (the length is right): this includes a flipped bit;
  - when no single byte explains the CRC (the length is right): a few wrong bits, that is a burst
    of up to 16 bits (it touches up to three bytes) or two wrong bits anywhere in the track.

The length of the data is the one that the next valid track header gives. When no valid header is
found where the data end, or one byte further on (the header there is damaged, or the file is
damaged there), the length that the track itself declares is used: a damaged header next to
damaged data does not stop the repair. The last track has no next header: the end of the file
gives its length, and a file that is one byte short or one byte long is repaired like any other
track.

For a wrong byte the CRC-16 points at the candidates, so only the few positions that can explain
it are tried. The corrections of bits are not searched but solved from the CRC: for every position
there is one candidate, which is then unpacked and checked. The checksum is only 16 bits and a sum
of bytes, so these corrections are accepted under rules that keep a wrong one from passing for a
right one:

  - In the modes that keep a dictionary (quick, medium, deep, heavy) a candidate must also make
    the unpacked data end where the packed data end: a stream that has gone out of step does not.
  - The candidates are tried in classes, the ones that flip the fewest bits first: bursts of 2 to
    8 wrong bits, then pairs of wrong bits far from each other, then bursts of 9 to 16 bits. A
    correction is taken only if exactly one candidate of its class gives the right checksum.
  - If the track unpacked as it is still ends where the packed data end (the damage is in the bits
    of literals and does not put the stream out of step) the checksum cannot choose among many
    candidates: only bursts of up to 4 wrong bits are tried.
  - No compression and simple accept any data and their checksum alone is a weak validation
    criterion: all the candidates are tried, and a correction is accepted only if it is the only one
    that fits.
  - A class that exceeds the per-track candidate-decode limit (DMS_BITS_TRIALS) is skipped. A
    correction found in a later class has not been compared with the candidates of the class that
    was skipped, which flip fewer bits: it is taken, but the track is shown as not verified and the
    report says so. (In no compression and simple a skipped class means that no correction is taken:
    it could not be shown that the correction is the only one that fits.)

More damage than this (three wrong bytes, a damaged sector) is not repaired: with so many possible
corrections, one that fits the CRC and the checksum could well be a wrong one. The track is then
kept as unpacked (best effort). The checksum is 16-bit, so in rare cases a correction
that is not the right one passes it; the report says what was changed and where.

In the modes that accept any data (no compression and simple) a wrong byte of any value can also
be "repaired" with another byte that gives the same sum, and the track then looks right. When the
track holds random data (data that were already compressed, for example) and the wrong byte has
any value, about one repair in twenty is wrong. The report names the byte that was replaced, so
that a repair can be checked.

The repair search is bounded by 6 seconds of repair work and 400,000 candidate decodes per archive
(DMS_REPAIR_SECONDS and DMS_REPAIR_BUDGET in the source). Only repair work counts toward this time:
key search and ordinary track decoding do not use it. The search for wrong bits is limited to 40,000
candidate decodes and one second per track (DMS_BITS_TRIALS and DMS_BITS_SECONDS), and can use at
most half of the archive-wide repair time and decode budget. This leaves resources for repairs that
require only one byte to be corrected. A class that exceeds the per-track limit is skipped (see
above). The report identifies searches stopped by a limit or classes that were skipped.

Encrypted archives. A DMS archive can be encrypted with a password. The plug-in does not ask for
it: the data of an encrypted archive are decrypted with a key that runs through the packed data of
the tracks, and the plug-in finds the key of the first disk track from its checksum. When the
first track is a normal disk (the boot block starts with "DOS") the search is short; otherwise the
65536 possible keys are tried. The key then follows the data of the next tracks, also across a
track whose packed data were repaired. The search is limited to 30 seconds (DMS_KEY_SECONDS in the
source), apart from the time of the repairs: if the limit stops it the archive is shown as damaged
and the report says why. If the header of the archive is damaged, the flag of encryption is read
as it is and the first track decides (an archive marked as encrypted whose data are not encrypted
is read as it is). A key changes only the first 20 bytes or so of the first track, so in the
modes that accept any stream (no compression and simple) a wrong key can have the right checksum.
The search then counts the keys that fit: if only one gives a boot block that names its root block
(880 or 1760) it is taken, and if only one fits it is taken; otherwise the first one is taken, the
track is shown as not verified and the report says that its first bytes are not certain. In the
other modes a wrong key almost never gives the right checksum, and the first key that fits is
taken. A key that gives the right checksum but not the end of the packed data (the unpacked data
do not end where the packed data end) is taken only when no other key fits, because the data may
be damaged at their end; the track is then shown as not verified and the report says so, since a
search through the 65536 keys finds about one such key by chance, even when the right one is not
among them. If no track can be decrypted, a box says that the archive is encrypted and its key was
not found.

Truncated and partly damaged data

  - The data of a track are delimited by the next valid track header. A truncated last track is
    unpacked as far as it goes.
  - In the modes that keep a dictionary from one track to the next (quick, medium, deep, heavy),
    the dictionary is uncertain after a track that was lost or damaged. A track that follows a
    lost or damaged one is unpacked with the dictionary that the previous tracks left and, if its
    checksum is not right, once more from an empty dictionary, which gives the right track when
    it does not need the lost data, so the loss of one track does not spoil every track after it.
    A track that cannot be verified is kept as unpacked (best effort), so that the tracks that
    copy from it are not lost too. The report says when a track was unpacked from an empty
    dictionary.
  - The decoders are bounds-checked and accept what real archives contain: a last run or a last
    match that goes past the end of the track is clipped, and an incomplete table of distances in
    the heavy modes is read as "repeat the last distance". The report says when a track needed
    such a tolerance. If the checksum of a heavy track that needed one of these two tolerances is
    not right, the track is read again the other way (the last match completed past the end of
    the track, the incomplete table read as a Huffman code in which what is not assigned is
    symbol 0), and the reading whose checksum is right is the one taken.
  - A track that appears twice in the archive is shown once: the copy that is verified is
    preferred, or else the first one.


6. DAMAGED ADF DISKS
----------------------------------------------------------------------------------------------------

The reader of ADF images goes on where a plain reader would give up:

  - Size. An image whose size is not a multiple of 512 bytes (truncated, or with extra bytes at the
    end) is read: the whole blocks are used.
  - Bootblock. A bootblock that is not "DOS" (the custom bootblocks of games and demos) does not
    matter when the root block is valid.
  - Root block. A root block with a wrong checksum is accepted when its hash table still points at
    header blocks of the image. If there is no usable root block at all, the image is scanned for
    file headers (see _RECOVERED below).
  - OFS or FFS. The flavor is read from the data blocks, not only from the bootblock: a bootblock
    that says FFS on a disk whose files have OFS data blocks is read as OFS.
  - OFS data blocks. When the block table of a file is damaged, lost, or points at a block of
    another file, the data blocks are found by (file header, sequence number). A size field that
    makes no sense is replaced by the size computed from the data blocks. Every data block is
    checked against the file that uses it, and the file is shown as incomplete or unverified when
    a block has to be used although a check failed:
      - a block that is a data block of another file, or of another place of the same file, is
        not used (the report says so) and its place is zero, unless the right block is found by
        (file header, sequence number);
      - a data block with a wrong checksum is used as it is;
      - a block that holds less data than the file needs there is used as far as it goes, and the
        rest is zero;
      - a block whose header is damaged gives its data as they are.
    A block of the table that is not a data block (a header, an extension or a directory cache
    block, for example) is not used either. When two blocks claim the same file and place, the one
    with a right checksum is used, else the one with the lowest block number, and the report says
    how many blocks were left out.
  - Checksums of the blocks of the structure. A file header or an extension block with a wrong
    checksum is reported; the data of the file are still used, and the file is shown as incomplete
    or unverified. A directory header with a wrong checksum is reported and counted as a damaged
    block (Bad Sectors).
  - Block chains. Pointers outside the image, blocks that are not headers and cycles in the hash
    chains are reported; the other entries of the directory are still read.
  - No root block and no file header. A disk of which neither the root block nor any file header
    is left, but that still has OFS data blocks with a right checksum, is rebuilt from those
    blocks: the files appear in _RECOVERED as DATA_<block>.bin (the names are lost with the
    headers, and so is the exact size: it is the size of the data blocks).

The _RECOVERED folder. Files and data that the directory tree does not reach appear in the folder
_RECOVERED, in the root of the panel:

  - every file header that the tree does not reach is a file. Its path is rebuilt from the parent
    pointers, through the directory headers that are still there, so the folders appear too;
  - in an OFS disk, the data blocks of a file whose header is lost are grouped by the header they
    name, ordered by sequence number, and shown as DATA_<block>.bin. Missing sequence numbers are
    zeros.

The recovery cannot tell a lost file from a deleted one: a file that was deleted from the disk but
whose blocks are still there can also appear in _RECOVERED. That is the price of finding the files
that really were lost.

The Description column and the information panel say which items could not be read completely or
could not be verified, and _RECOVERY_REPORT.txt lists what was found and repaired.


7. LIMITS
----------------------------------------------------------------------------------------------------

  - Read-only: nothing can be written, deleted or created inside an image or an archive.
  - Only the Amiga OFS and FFS file systems are read (not PFS, SFS and other ones).
  - The whole image is held in memory: an ADF or a DMS archive of up to 512 MiB; a DMS archive is
    also unpacked in memory. In the 32-bit version a very large image may not fit in the address
    space of Far: a box then says that there is not enough memory.
  - Names of up to 30 characters (the Amiga limit) are shown, converted as described in section 4.
  - Only the last modification date is read (not the creation date of the disk or the date of the
    root block); protection bits and file comments are not read.
  - Directories nested more than about 60 levels deep are not entered.
  - DMS archives without a disk image are refused (section 3), and so are encrypted ones whose
    key is not found and from which nothing can be unpacked.
  - If a memory allocation fails, the call that needed it is lost, Far goes on.
  - The effort limits for repairs (DMS_REPAIR_SECONDS, DMS_REPAIR_BUDGET, DMS_BITS_TRIALS,
    DMS_BITS_SECONDS), the time limit for the search of the key of an encrypted archive
    (DMS_KEY_SECONDS) and the largest file that is opened (MAX_FILE_SIZE) are set at the top of the
    source and can be changed there.


8. LANGUAGES
----------------------------------------------------------------------------------------------------

Every text that the panel shows (the "[damaged]" suffix of the title, the labels and values of the
information panel, the descriptions of the items, the boxes that say why a file is not opened or
that the panel is read-only, the copy dialog) comes from a Far language file (.lng) in the folder
of the DLL.

  ADFDMSViewEng.lng   English

How it works

  - Far loads the file whose ".Language=" line names its interface language (Options > Languages).
    If there is no such file, it loads the English one.
  - The English texts are also built into the DLL. Without any language file, the plug-in works in
    English.

Adding a language (no recompilation is needed)

  1. Copy ADFDMSViewEng.lng to ADFDMSView<Language>.lng in the folder of the DLL.
  2. On the first line, change the language to the name that Far uses for it (the word before the
     comma, for example "German"; the text after the comma is only a description).
  3. Translate the text of each message, between the double quotes.
  4. Save the file as UTF-8 with BOM, and restart Far.

Rules for a language file

  - A message is a line that starts with a double quote. Far numbers the messages from 0 in the
    order in which they appear, and the plug-in asks for them by number: keep every message, in the
    same order. A file with fewer messages than the DLL expects makes Far report a bad language
    file.
  - Lines that do not start with a double quote (the // lines) are comments.
  - Keep the placeholders (%u, %d, %ls) in the same order and of the same type as in the English
    text. The comment above each message says what its placeholders are. A translation whose
    placeholders differ from the English ones is not used: the English text is shown instead, so
    a mistake cannot make Far crash.
  - Do not use double quotes or backslashes inside a message, except the \" (an escaped double
    quote) in the messages that already have it.

What is not translated

  - The recovery report (_RECOVERY_REPORT.txt) is written by the engine and is always in English.
  - The names of the special items (_RECOVERED, _RECOVERY_REPORT.txt, <name>.adf) are the same in
    every language.


9. BUILDING FROM SOURCE
----------------------------------------------------------------------------------------------------

The plug-in is a single C file, adfdmsview.c, plus the version resource adfdmsview.rc. Run build.bat
from the Windows Command Prompt; it changes to its own folder, so the caller's current directory
does not matter. The script builds the 32-bit and 64-bit DLLs with the MSYS2 GCC toolchains.

Commands

    build.bat              builds both versions
    build.bat x64          builds only .\x64\ADFDMSView.dll (64 bit)
    build.bat x86          builds only .\x86\ADFDMSView.dll (32 bit)
    build.bat noupx        builds without UPX compression
    build.bat max          also asks UPX to try --ultra-brute (much slower; not with noupx)
    build.bat zip          creates ADFDMSView-<version>.zip (needs tar.exe)
    build.bat x64 max zip  options can be combined

MSYS2

  - The script searches for MSYS2 in MSYS2_ROOT, C:\msys64, C:\msys2, drives C: to G: and the
    registered MSYS2 installation path. Set MSYS2_ROOT when it is installed elsewhere.
  - If MSYS2 is not found, the script offers to download and install it unattended. This offer is
    made only on x64 Windows 10 version 1809 (build 17763) or later, when curl.exe is available
    and the destination folder is missing or empty. The default destination is C:\msys64 (or the
    folder named by MSYS2_ROOT).
    Answer 1 to download and install; answer 0 to leave the system unchanged and show
    https://www.msys2.org. The installer is obtained from the official MSYS2 installer project,
    runs silently, and the new installation is updated with pacman before building. MSYS2 recommends
    a short ASCII-only path on an NTFS volume, without spaces or network drives; the default
    C:\msys64 is the safest choice. See https://www.msys2.org/docs/installer/.
  - On other Windows versions, the script does not attempt an automatic installation. Check the
    current MSYS2 Windows support requirements before installing it manually; an existing compatible
    installation can be selected with MSYS2_ROOT.

C compilers

  - For x64, the default environment is MINGW64 only (package mingw-w64-x86_64-gcc). It is
    deliberately used because it produces substantially smaller DLLs for this plug-in. UCRT64
    (mingw-w64-ucrt-x86_64-gcc) is not selected automatically. If MINGW64 is missing, the
    installation menu offers MINGW64 and UCRT64 and requires an explicit choice. You can also set
    ENV64=ucrt64 to force UCRT64, or set "ENV64=mingw64 ucrt64" in cmd.exe to search MINGW64 first
    and UCRT64 second. MSYS2 is phasing out MINGW64, so package availability may change over time.
  - For x86, the environment is MINGW32 and the package is mingw-w64-i686-gcc. MINGW32 is a
    legacy 32-bit environment whose package availability has gradually been reduced. It is still
    needed to produce the 32-bit Far plug-in.
  - A toolchain is considered available when both gcc.exe and windres.exe are present. If none of
    the requested environments has them, the script lists the GCC packages it knows for that target
    and asks which one to install with pacman. Choose 0 to skip that DLL. After installation it
    checks for the compiler and resource compiler again.
  - ENV64 and ENV32 can change the environments to try, in order. By default ENV64=mingw64, so
    UCRT64 is never selected implicitly. Set ENV64=ucrt64 to force it, or ENV64="mingw64 ucrt64" to
    allow it as a fallback after MINGW64. For x86, use ENV32=mingw32. These names are
    target-specific.

Far Manager SDK header (plugin.hpp)

  - The project-folder plugin.hpp is checked first. If FARSDK is set, the script checks that folder
    and its Headers.c subfolder; if the header is not there, it stops and reports the wrong path.
  - When FARSDK is not set, the script checks PluginSDK, its Headers.c subfolder, and the
    PluginSDK\Headers.c folder of an installed Far Manager.
  - If it is still missing and FARSDK was not explicitly set, the script downloads plugin.hpp from
    the official Far Manager repository into .\PluginSDK. This needs curl.exe. The downloaded
    header is kept there for later builds.
  - FARSDK can name the folder containing plugin.hpp or the Headers.c subfolder itself. If FARSDK
    is set but no header is found there, the script reports the problem instead of silently using a
    different SDK folder.

UPX compression

  - By default the script searches UPX_EXE, PATH and the MSYS2 folders. If UPX is missing, it tries
    to install the native MSYS2 UPX package with pacman. This host-tool package selection is
    independent of the GCC environment used to build the DLL. If UPX cannot be installed, the DLL is
    still built unpacked and a warning is shown. Use noupx to skip the search and installation
    entirely.
  - Normal compression uses --best --lzma. When packing succeeds, the build log reports the DLL
    size before and after UPX. If UPX fails, the saved unpacked DLL is restored and a warning is
    shown. With max, UPX is run with --best --ultra-brute --lzma; this tries more variants and can
    take substantially longer. It does not guarantee that every DLL will become smaller. max and
    noupx cannot be used together.
  - Before packing, the script saves a temporary copy of the unpacked DLL. If UPX fails, that copy
    is restored, so a failed packing attempt does not leave a damaged or partially written DLL.

Other checks and files

  - The version in Info->Version in adfdmsview.c must agree with VER_MAJOR, VER_MINOR, VER_PATCH
    and VER_BUILD in adfdmsview.rc. VER_STRING must also match the same major.minor.patch version
    (the build number is appended only when it is not zero). The build stops on a mismatch.
  - The resource is compiled with windres and linked into the DLL. The script checks that the 14
    Far entry points are exported with their expected undecorated names, using objdump when it is
    present in the selected toolchain. If objdump is missing, this export check is skipped with a
    warning.
  - The language files (ADFDMSView*.lng) are copied next to each DLL. Each output folder is ready
    to be copied into Far's Plugins folder.
  - zip includes the user documentation, the license file and the output folders that were built.
    It requires tar.exe in PATH (normally included with Windows 10 and later); the license file
    must be present before building the package.

Optional environment variables

    MSYS2_ROOT   MSYS2 installation folder (default C:\msys64)
    MSYS2URL     URL of the MSYS2 x86-64 installer used for unattended installation
    ENV64        x64 environments to try, in order (default: mingw64 only)
    ENV32        x86 environments to try, in order (default: mingw32)
    FARSDK       folder containing plugin.hpp, or its Headers.c subfolder
    UPX_EXE      full path to upx.exe (otherwise PATH and MSYS2 folders are searched)

The compilers, windres, objdump and UPX are supplied by MSYS2 packages and are installed with
pacman when needed, except that UPX installation is best-effort: the DLL can still be built without
it. Some antivirus programs are suspicious of UPX-packed files; use noupx for a plain DLL.

The engine alone (the DMS unpacker and the ADF reader, without Win32 and Far headers) can be built
with gcc -DADF_CORE_ONLY ... .
